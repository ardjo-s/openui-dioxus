# Define the canonical runtime domain contract

Type: `grilling`
Status: `resolved`
Blocked by: 02, 03, 05

## Question

What are the canonical boundaries and invariants for surfaces, component catalogs, streaming updates, state, typed actions, validation, stabilization, replay, schema versions, and migrations?

## Answer

OpenUI remains the public language. Rust keeps two different records on purpose: an immutable OpenUI program for applying future patches correctly, and an immutable Surface revision for rendering and execution. Dioxus only displays those verified structures. Anything that can touch the outside world passes through the host as a typed, recorded effect.

`v0.1` favors the smallest contract that stays true under failure: no generated interaction while a stream is unfinished, no guessed state deletion, no partially committed broken patch, no dynamic untrusted component plug-in, and no claim of eternal or pixel-identical replay.

## Decisions

- **Q1 — Two records, two jobs.** OpenUI remains the public language and interchange contract. Each accepted replacement or patch creates an immutable `OpenUIProgramRevision`: the complete OpenUI program and the only legal base for later source patches. Rust derives an immutable `SurfaceRevision`, the only structural input allowed for rendering, actions, and replay. Runtime state and results do not mutate either record; a displayed state is a `RenderProjection` composed from one Surface revision and one semantic-event watermark. This internal split must preserve observable OpenUI semantics and must not become a competing public protocol.
- **Q2 — One guarded door for every effect.** The OpenUI adapter frames, parses, and merges language input. The Rust runtime validates, sequences events, owns semantic state, checks policy, and stabilizes revisions. The catalog supplies trusted, compiled, pure view adapters. Dioxus renders and emits typed user events. The application host alone performs every host-visible effect through an `EffectInvocation`, including queries, mutations, resource retrieval, navigation, URL opening, and assistant handoff. Catalog components may not perform hidden I/O, read clocks or randomness for semantics, navigate directly, or keep persistent semantic state.
- **Q3 — Pin executable behavior, not only component names.** Every committed Surface binds an immutable catalog release that fixes its `catalog_contract_version`, schema and semantics hashes, catalog release hash, adapter build, execution profile, Dioxus version and target, and resource capabilities. `v0.1` accepts only trusted components statically compiled into the host and makes no stable Rust ABI promise. Replay never resolves a floating “latest” catalog.
- **Q4 — Structural revisions never lie about history.** A Surface keeps one stable identity. Every structural version published to Dioxus is an immutable, numbered Surface revision with parent, phase, and content hash. A streamed revision may be `provisional`; only an atomically committed revision may receive generated interactions. State or result changes advance the semantic event sequence, not the Surface revision number. Compaction may remove an unreferenced revision body or delta, but never its identity, parent, phase, hash, or event references.
- **Q5 — Stream only closed, harmless pieces.** During streaming, the runtime may publish only a whole named-statement subtree that is syntactically framed, dependency-closed, catalog-valid, and inert. Missing or invalid regions stay absent; host-owned loading UI is not invented OpenUI content. OpenUI's document-wide partial marker is not treated as node readiness. A provisional stream is recorded but cannot commit external behavior.
- **Q6 — Semantic identity is not a Dioxus key.** Runtime `InstanceId` identifies continuity for stateful or actionable occurrences and reorderable repeated items; an OpenUI statement name and a list position are never used as substitutes. Repeated durable items require a catalog-declared stable data key or fail validation. Dioxus reconciliation keys are derived separately, and every sibling in a keyed group must have a unique key. Presentational nodes need no durable `InstanceId`, even when rendering requires a Dioxus key.
- **Q7 — State belongs to one session and one Surface.** A state address is `(session_id, surface_id, exact OpenUI $name)`. Existing values survive Surface revisions and win over later defaults. Removing a source declaration never deletes its stored value. `v0.1` supports OpenUI `Set` and reset-to-declared-default semantics, plus teardown of the whole session namespace; it introduces no extra per-key deletion command. Type conflicts are checked against explicit typed use sites, not guessed from a default value, and fail visibly instead of coercing or losing data.
- **Q8 — No generated controls during an unfinished stream.** The language adapter still preserves OpenUI streaming semantics, but the `v0.1` renderer capability declares `stream_local_interaction = false`: generated controls remain disabled until the update commits and final validation passes. No query, mutation, resource fetch, navigation, or other effect starts earlier. Early local interaction or early reads may be negotiated as separate future renderer or host capabilities; neither is part of strict `v0.1` execution.
- **Q9 — Claim intent before doing work.** An `ActionInvocation` binds the committed source Surface revision, durable target identity, typed arguments, minimal required state, action-plan hash, catalog contract, and policy decision. The runtime atomically compares those facts with the current head and records the claim before dispatch. Any mismatch makes the action stale and requires fresh user intent; a later revision can never retarget an already prepared invocation.
- **Q10 — One receipt per external step.** An OpenUI action plan is an ordered list of local and external steps. Every external step creates its own durable `EffectInvocation` in `prepared` state before host dispatch and its own receipt: `succeeded`, `failed`, `denied`, or `unknown`. Unique action, step, and effect IDs provide runtime deduplication. Host-level exactly-once behavior exists only when the host declares an idempotency capability. `unknown` stops the plan and is never retried automatically; an action-level receipt may summarize, but never replace, step receipts.
- **Q11 — A broken update loses as one unit.** OpenUI patch merge operates on the whole program, so `v0.1` quarantines or rejects the complete update operation rather than committing a hand-built mixture of old and new blocks. The last committed Surface remains authoritative; provisional streamed revisions are abandoned as the active head while their required history metadata remains, and any fallback is host-owned UI outside the canonical Surface. End users get a simple explanation while structured diagnostics feed developers and the correction loop. Block-level partial commit is deferred until a real dependency graph can prove it safe.
- **Q12 — Errors have stable identities.** Validation emits blocking or advisory diagnostics. Language meaning, catalog types, state and action integrity, host policy, resource policy, and required accessibility rules are non-demotable blocking floors. Catalogs and hosts may make an advisory rule stricter, never weaken a floor. Each diagnostic carries a stable fingerprint derived from rule ID, normalized location, and compatibility identity so replay, tests, and correction can compare the same problem reliably.
- **Q13 — Migrate complete worlds, preserve inert archives.** A `CompatibilityVector` names every behavior-affecting version. Each migration edge declares one exact source vector and target vector and is deterministic, side-effect-free, copy-on-write, independently validated, and recorded with provenance. Ordered graph paths are allowed; independent migrations are never assumed to commute. `v0.1` defines this seam and fixtures but invents no migration before a contract changes. An archive remains inspectable and exportable, with an optional self-contained inert preview; interactive execution needs direct support or a validated migration and is not promised forever.
- **Q14 — “Saved” and “replayable” are different seals.** A stabilized Surface is committed after end-of-stream with no blocking diagnostic and a pinned compatibility vector. A checkpoint seals one such revision and all policy-authorized semantic inputs and outcomes through an event watermark, with no unresolved invocation. `full` means executable replay has every behavior-affecting dependency. `redacted` and `partial` are audit replays that carry an omission manifest and halt explicitly at the first missing dependency. Captured assets are content-addressed and hash-verified; raw data forbidden by capture policy is never smuggled into a checkpoint.
- **Q15 — Repair candidates are data, never live UI.** The runtime reports diagnostics but never calls a model. An application-owned correction orchestrator may ask a model under explicit attempt, time, and cost limits; the `v0.1` default is at most two attempts. Progress means a monotonic reduction in blocking diagnostic fingerprints. Repeated or non-improving candidates stop the loop. Every candidate is parsed and validated as data, never mounted, never allowed to trigger effects, and never generated during replay.
- **Q16 — Replay is semantically exact and physically inert.** Replay executes stored Surface revisions, semantic state/events, classified captured results and resources, and effect receipts through an inert renderer. It cannot call a model, tool, network, navigation handler, ambient image fetch, or host effect. OpenUI source and program revisions remain patch history and audit evidence; reparsing may verify hashes and semantic equivalence but cannot rewrite replay history. A mismatch is an explicit divergence. Exactness means the same supported semantics, not identical pixels across operating systems or WebViews.
- **Q17 — Patch the program, commit program and Surface together.** Every update declares `full replacement` or `named-statement patch` before streaming, plus an operation ID and expected `OpenUIProgramRevision` base. Chunks belong to that operation only. Patch evaluation uses the pinned whole-program OpenUI merge semantics. On success, the new Program revision and derived committed Surface revision become current atomically; on failure, neither does. The runtime never infers mode or patches a normalized Surface directly.
- **Q18 — One sequence orders every meaningful fact.** Each Surface has one monotonic semantic-event sequencer in `v0.1`, covering update commits, state changes, action claims, effect preparation and receipts, captured resource results, diagnostics, migrations, and checkpoints. Multiple actors may submit work, but stale expected bases fail with an explicit conflict. Last-write-wins, automatic semantic merge, CRDT collaboration, and silent rebasing are outside `v0.1`.
- **Q19 — Classify before logging.** Raw form state is transient trusted input only. Before any persistent write, the runtime derives a minimal typed execution projection and a separate capture projection whose fields are retained, redacted, or omitted by pinned catalog and host metadata. Missing classification means non-persistable. Credentials, tokens, keys, and equivalent secrets are never persisted; when execution needs one, durable records keep only a host-owned opaque reference or safe commitment. Raw form state never appears in logs, receipts, checkpoints, or exports; encryption does not override minimization or retention rules.
- **Q20 — Coalesce only what nobody observed.** Canonical replay records semantic events, not raw keystrokes, pointer movement, or gesture telemetry. Reversible local state changes may be coalesced only across an unobserved span. Action evaluation, policy checks, queries, resources, effects, diagnostics, revision commits, and checkpoints are observation barriers: all state they could observe becomes immutable history. Fine-grained telemetry is a separate optional capability, never canonical replay.
- **Q21 — Support is a complete compatibility vector.** Direct execution requires an explicit match across language profile, schema set, catalog contract, catalog schema and semantics hash, catalog release hash, adapter build and execution profile, Dioxus version and target, platform contract, host-action policy, resource policy, replay schema, and semantic-event schema—or a registered migration between exact vectors. Version numbers are never guessed into compatibility. A schema may mark an unknown field forward-ignorable; every unknown behavior-affecting element is must-understand and blocks execution. Unsupported artifacts remain archivable.

## Review during implementation

These are the active `v0.1` rules, not eternal assumptions. The [runtime contract decision-review register](../architecture/runtime-contract-review-register.md) records the evidence required to reopen each decision. In particular, Q8 must be measured from first provisional display to committed interaction; a slow stream does not silently relax the effect boundary.

## OpenUI v0.5 constraints

- Components have no unique rendered-instance key. A `statementId` is a source-definition name and can be reused or absent, so it cannot identify one visible component instance.
- Runtime state is addressed by exact `$name` keys. Existing persisted values survive reparsing and take precedence over declaration defaults; defaults fill only absent keys. OpenUI exposes `Set` and reset-to-declared-default behavior, not state deletion.
- Partial parsing reports document-wide incompleteness, not per-node completeness, and creates no explicit placeholder nodes.
- Streaming lifecycle and statement-patch merging are explicit mechanisms separate from ordinary parsing. A patch is merged as a whole program and unreachable statements may be collected globally.
- The language and catalog versions are not serialized in OpenUI Lang output; the enclosing capability and replay contracts must carry them.
- An action plan may mix local state changes with multiple ordered query, mutation, assistant-handoff, and URL-opening steps.
- An `ActionEvent` may expose every form field as raw form state, so persistence classification must happen before logging.
- Catalog renderers are executable implementations, not semantics fully captured by their JSON schemas.
- A catalog image may accept a remote source, and Dioxus desktop may open external schemes; rendering therefore needs an explicit resource and navigation boundary.
- Dioxus reconciliation requires keys to be unique and consistently present within a keyed sibling group; its render key is not a durable domain identity.

## Adapter and platform implication

No Q1–Q21 decision is reopened. This clarifies Q2 and Q21: the runtime imports no concrete component or platform library; catalog adapters and renderer-side platform UI services remain pure, while every host-visible effect still crosses the typed application-host boundary. The complete adapter and host identities participate in compatibility and replay.
