# OPE-9 ecosystem-relative product-value research

Research date: 2026-08-25. This note does not make a product decision. It separates primary-source facts, bounded inferences, and unknowns that the evaluation must measure. Local links identify repository evidence; external links point only to official specifications, documentation, registries, or source repositories.

## 1. Protocol promptability

**Baseline boundary.** Typed JSON Dioxus is the primary product baseline: a closed schema derived from the local catalog and used as a generation control, not a public protocol. OpenUI Lang is the candidate language adapted into that catalog. A2UI is the comparable protocol result. Direct Dioxus/RSX and React/TypeScript code are compile-time implementation routes, not runtime-generated protocols.

**Facts.** This repository pins `@openuidev/lang-core@0.2.15` (npm tarball SHA-1 `33b9329a2ff962d5c77afeee63cf45a4296a906a`) and OpenUI source commit `c3c0d1b7cf1d58e01846e86b7e9706f54afb2511` ([npm registry](https://registry.npmjs.org/@openuidev/lang-core/0.2.15), [pinned source](https://github.com/thesysdev/openui/tree/c3c0d1b7cf1d58e01846e86b7e9706f54afb2511/packages/lang-core)). Its library contract generates catalog vocabulary, prompt material, and schema. The language also has streaming parsing, statement patches, state and expressions, and action plans. Host constraints are therefore not only syntactic: statement names are not visible-instance identities, patches apply to the whole program, partial parsing does not make every node safe to publish, and declarative actions do not authorize effects by themselves ([OpenUI v0.5 specification](https://github.com/thesysdev/openui/blob/c3c0d1b7cf1d58e01846e86b7e9706f54afb2511/docs/content/docs/openui-lang/specification-v05.mdx), [incremental merge source](https://github.com/thesysdev/openui/blob/c3c0d1b7cf1d58e01846e86b7e9706f54afb2511/packages/lang-core/src/parser/merge.ts)).

A2UI describes a declarative JSON format rendered through client-approved component catalogs. Its official repository identifies `v0.9.1` as the production version while also calling the project an early-stage public preview with a v1.0 release candidate ([official repository, accessed 2026-08-25](https://github.com/a2ui-project/a2ui)). The v0.9 evolution guide describes a prompt-first envelope, `createSurface` with `catalogId`, a flat identified component list, `updateComponents`, a data model, and structured `VALIDATION_FAILED` correction ([official v0.9 guide](https://github.com/a2ui-project/a2ui/blob/main/specification/v0_9/docs/evolution_guide.md)). Those are protocol constraints; they do not alone provide replay, migration, or effect-authorization semantics.

The frozen OPE-3 three-arm run already found `OPENUI_WIN` against A2UI and `TIE` against typed JSON over one 20-scenario, eight-component protocol corpus. Its report explicitly excludes product quality, maintenance, accessibility, and mobile claims ([local OPE-3 report](../../prototype/openui-a2ui-cloud-eval/evidence/three-arm-controlled-run-2026-08-24/RUN-REPORT.md)).

**Inference.** At equal closed-catalog scope, OpenUI may reduce prompt surface through its language and generated instructions. Typed JSON remains the necessary control for whether that syntax adds value beyond the same catalog contract. This result cannot be attributed to the Dioxus runtime.

**Unknowns.** No primary source proves that the frozen result generalizes to A2UI's current v1.0 candidate or to a broader production catalog. A new protocol run is justified only by a separately preregistered falsifiable change in protocol, prompt, validator, repair, or catalog semantics.

## 2. Constrained-runtime value

**Facts.** For a compile-known interface, Dioxus provides RSX components, typed props, and feature-selected renderers without an intermediate UI protocol or Surface interpreter ([Dioxus 0.7 UI](https://dioxuslabs.com/learn/0.7/essentials/ui/), [`dioxus::launch` 0.7.10](https://docs.rs/dioxus/0.7.10/dioxus/fn.launch.html)). React/TypeScript provides the analogous Web route through JSX/TSX, typed props, and TypeScript tooling ([React 19.2 TypeScript guide](https://react.dev/learn/typescript)). Ordinary framework code, tests, and review are strongest when interface structure and actions are already known at compilation.

The representative external dynamic-UI baseline is `vercel-labs/json-render v0.19.0`, official tag `0bbe6ed6394b23b5aee25320d03c9b7ac717e5b7`, rather than an ad hoc React renderer. Its official source provides typed catalogs, generated prompts, a React registry, constrained JSON, streaming, state, actions, prebuilt shadcn components, MCP integration, and additional renderers including React Native ([official source](https://github.com/vercel-labs/json-render/tree/0bbe6ed6394b23b5aee25320d03c9b7ac717e5b7), [official MCP integration](https://github.com/vercel-labs/json-render/blob/0bbe6ed6394b23b5aee25320d03c9b7ac717e5b7/skills/mcp/SKILL.md)). Each renderer claim still requires its own evidence.

The proposed constrained runtime adds value only through guarantees that direct code and a renderer library do not automatically supply: immutable OpenUI program history separated from `SurfaceRevision`, atomic patch validation, a closed compiled catalog, semantic event ordering, typed effect invocations and durable receipts, inert replay, complete compatibility vectors, and deterministic copy-on-write migrations ([local runtime contract](../decisions/06-define-runtime-domain-contract.md)). The OPE-4 catalog makes part of that cost visible by generating an OpenUI `LibrarySpec`, JSON Schema, prompt, documentation, static Rust registry, and release hashes from one manifest ([catalog evidence](../../prototype/dioxus-components-catalog-eval/README.md)).

**Inference.** The constrained runtime can add product value when interface structure, data shape, actions, or revisions are unknown at compilation and must remain validated, auditable, non-executable data. For a compile-known screen, it adds Surface, adapter, compatibility, and replay work; direct RSX must therefore be allowed to win that cohort. `json-render` is a credible external dynamic baseline because it already addresses catalog-constrained streaming UI rather than merely rendering arbitrary JSON.

**Unknowns.** Neither Dioxus, OpenUI, A2UI, nor `json-render` proves exact replay, migratable archives, lower correction time, better UI quality, or lower total ownership cost for this product. Those outcomes require shared workflows and explicit evidence rather than feature-list inference.

## 3. Design-system onboarding and maintenance

**Facts.** An agent-compatible catalog is not automatic component discovery. A2UI requires client-approved components and a catalog identity; OpenUI exposes a library and prompt contract, while trusted host renderers still own behavior ([A2UI repository](https://github.com/a2ui-project/a2ui), [OpenUI library source](https://github.com/thesysdev/openui/blob/c3c0d1b7cf1d58e01846e86b7e9706f54afb2511/packages/lang-core/src/library.ts)).

The local 12-component manifest generates both the strict typed-JSON schema and OpenUI artifacts, keeping one catalog source while separating serializable wire props from real Dioxus props ([bridge decision](../decisions/07-design-the-design-system-bridge.md), [catalog manifest](../../prototype/dioxus-components-catalog-eval/catalog/manifest.json)). Every onboarded component still needs reviewed generation semantics, usage rules, events, accessibility behavior, fixtures, and a compiled adapter.

The second real Dioxus catalog selected for maintenance measurement is Rust/UI at snapshot `7fd792520ba5e3ad5354c26ac4e6816c2d156b7c`, accessed 2026-08-25. Its official source describes a shadcn-inspired component registry copied and customized into an application, with Web, Desktop, iOS, and Android ambitions ([official source](https://github.com/rust-ui/ui/tree/7fd792520ba5e3ad5354c26ac4e6816c2d156b7c), [official Dioxus documentation](https://dioxus.rust-ui.com/)). The evaluation must verify selected components and targets rather than promote those claims into certification.

Design tokens address theme exchange, not component behavior. DTCG `2025.10` is a pre-standard format reference for tokens, not proof of correct component, action, or accessibility conversion ([DTCG format module](https://www.designtokens.org/TR/2025.10/format/)).

**Inference.** The bridge has maintenance value only if one reviewed declaration measurably prevents drift between prompt, schema, documentation, fixtures, and registry across catalog changes. It is negative value if teams with stable compile-known UI must maintain parallel contracts without runtime-generation benefit. React, Figma, JSON, and screenshot conversion must remain inert drafts until human review, compilation, tests, and certification.

**Unknowns.** The repository has not measured a second real catalog's active onboarding time, adapter churn, review defects, migration work, or accessibility burden. The existing thin swap is a seam proof, not a maintenance-cost result.

## 4. Cross-platform leverage

**Facts.** This repository pins Dioxus `0.7.10` at `57d6794ad60b949e5bd8aa282f6f8c3dc97a365e`. Dioxus exposes separate Web, Desktop, and Mobile features: Web uses WASM and the DOM; Desktop runs Rust natively with a WebView; Mobile uses the Desktop engine plus platform toolchains ([Dioxus platform guide](https://dioxuslabs.com/learn/0.7/guides/platforms/), [mobile guide](https://dioxuslabs.com/learn/0.7/guides/platforms/mobile/), [v0.7.10 source](https://github.com/DioxusLabs/dioxus/tree/v0.7.10)). First-party renderers currently target HTML/CSS; native widgets need separate integrations, and the native renderer remains emerging ([Dioxus escape hatches](https://dioxuslabs.com/learn/0.7/essentials/ui/escape/)).

The confirmed leverage is shared Dioxus trees, CSS, state, and some logic, not automatic equivalence. Android/iOS toolchains, WebViews, navigation, focus, keyboards, safe areas, permissions, lifecycle, and renderer behavior remain target-specific. Dioxus 0.7 migration notes also show renderer-specific behavioral changes ([Dioxus 0.7 migration](https://dioxuslabs.com/learn/0.7/migration/to_07/)).

**Inference.** OpenUI-Dioxus can amortize Dioxus portability only if its Surface and catalog remain independent from platform services and `PlatformHost` declares adaptations and refusals. It does not create Dioxus's cross-platform leverage. Its potential contribution is preserving the same validation, action, receipt, and replay semantics for runtime-uncertain UI across targets.

**Unknowns.** Compilation is not interaction or accessibility evidence. Screen-reader parity, focus, touch, virtual keyboards, safe areas, suspend/resume, physical devices, and catalog-specific wrappers remain unproven until independently exercised on each claimed target.
